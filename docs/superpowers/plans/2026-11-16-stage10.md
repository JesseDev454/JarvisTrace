# Stage 10 PostgreSQL visual retrieval implementation plan

> Execute inline using the existing environment and test-driven development.

**Goal:** Index source frames and optional detector crops with OpenCLIP, then
retrieve timestamped visual matches from PostgreSQL using natural-language text.

**Architecture:** Extract the existing encoder behind compatible imports. Keep
database configuration independent of the prototype FastAPI app. Use a checked
Alembic baseline and a new typed visual table; existing scene/text data stays
unchanged. CLI operations run outside request handlers.

**Tech stack:** Installed Python, OpenCLIP, OpenCV, Pillow, psycopg, pgvector,
SQLAlchemy/Alembic; no package upgrades or new downloads.

**Spec:** Master brief Stage 10; `docs/ARCHITECTURE.md` and `docs/PROJECT_AUDIT.md`.

## Global constraints

- Preserve all existing tables/records and Stage 1–9 functionality.
- CLIP ViT-B-32 image/text vectors share their own 512-dimensional space.
- MiniLM 384-dimensional scene vectors remain separate.
- Model/preprocessing identity, content hashes, timestamps and crop provenance
  accompany every visual embedding. Detector crops remain unreviewed predictions.
- Do not load VLMs or put indexing in request handlers. Reuse cached CLIP weights.
- Do not claim accuracy or absence detection from one synthetic clip.
- Database migration is explicit, backed up, restore-tested and non-destructive.

## Review focus

- Mismatched encoder dimensions/model settings must fail or return no compatible rows.
- Repeat imports must preserve unique samples without duplicating embeddings.
- Wrong source video, bad boxes/frames, invalid vectors and partial failure must fail safely.
- Camera, video and timestamp predicates must apply before result ranking.
- Crops and full frames from one timestamp must not dominate duplicate result slots.
