# Stage 12 Search and Playback Implementation Plan

**Goal:** Let Goodluck search indexed recordings and play ranked time windows locally.

**Architecture:** A separate loopback FastAPI app wraps the read-only Stage 11
function. A plain HTML/CSS/JavaScript page provides filters, ranked cards, evidence
and native video playback. Opaque recording IDs resolve only pinned indexed
sources contained in configured storage roots; byte-range support enables seeking.
No indexing, caption generation or database migration runs in the app.

**Tech stack:** Existing FastAPI/Starlette/Uvicorn, PostgreSQL and cached encoders;
native browser media. No extra frontend dependencies.

## Design decisions

- Existing prototype API also writes scenes; extending it would expose unrelated
  write operations. A dedicated read-only app keeps Stage 12 focused. A React
  rewrite adds tooling without helping this first playback flow.
- User has requested proceeding with the specified next stage and previously
  delegated routine choices. Continue in the shared checkout on a new codex branch,
  carrying required uncommitted Stage 11 changes and preserving unrelated tests.
- Local-only access is intentional. Remote deployment needs authentication before
  binding outside loopback; the CLI offers no public bind option.
- Expose source IDs, camera, relative video times and score explanations. Never
  expose filesystem paths. Show relevance limitations alongside results.
- Use native source playback first; unsupported browser codecs show an actionable
  error. No silent transcoding or changes to source recordings.
